# sssync 设计文档 v0.2

> 两台 Mac 的「整机状态」手动同步器。Swift 编写，引擎 + agent + SwiftUI 界面。
> 状态：M1、M2 的主体已实现（2026-11-06）：文件 / 目录 / 启动项模板 / 默认打开方式，三方合并，环境与应用对比（本机缺的可补齐 / 升级，本机多的可卸载，都只改本机），确认差异，菜单栏常驻与通知。App 偏好逐键同步与录制已下线（2026-11-06）：全量扫描把系统注入项和每台必异的数据都当成差异，且写入要求 App 退出，收益抵不过噪音。未做：整次撤销、收件箱、噪音学习、Mackup 导入、App 跨机传包。只支持 macOS。

---

## 0. 定位

把家里 MacBook 和公司 Mac mini 摆在一起，看清两边哪里不一样、是哪边改的，由我逐条决定以谁为准，然后安全地执行。

**管的东西**：文件、Shell 环境（zsh 配置、环境变量）、开发工具链（nvm 的 node 版本与全局包、uv 的 Python 等）、启动项（含同名不同参）、App 本身、默认打开方式。App 的偏好设置不逐键同步，走文件 / 目录条目或 App 自带的同步。项目代码不管（只用 git）。

**核心原则**

1. **手动、可见、可撤销**：不点执行什么都不发生；覆盖前必备份；能整次撤销。
2. **永远由我拍板冲突**：禁止按修改时间判断，禁止「新的赢」，禁止自动选边。
3. **每一条都能单独设策略**，粒度到文件或启动项。
4. **拍板的单位是「条目」**，不是文本行。

## 1. 决策记录（为什么这样定）

| 问题 | 结论 | 理由 |
|---|---|---|
| 用现成工具还是自建 | **自建对账与决策层**，底层操作用现成的 | 同名不同参的模板、冲突永远问我——Unison / unisync / Mackup / chezmoi 都做不到 |
| Unison 当底座、上面包编排层？ | **不行** | 整文件覆盖会把本机专属的窗口位置、路径一起带过去，没法只挑一部分；同名启动项整文件同步会把家里的端口和密钥写到公司；自己的对账器加 Unison 的 archive 是两份真相；编排层一旦围绕 Unison profile 写，「以后换引擎」做不到 |
| 自写同步会不会在正确性上翻车 | 风险可控 | Unison 啃的是任意大目录、部分传输这类通用问题；我们管的是固定的小名单，靠「备份 → 临时文件 → 校验 → 原子改名 → 逐条记账 → 会话日志」保证安全（§5.3） |
| fork dvcrn/unisync | **不 fork** | 9 个 Go 文件，核心是调 unison 命令；架构是「本机 ↔ 中转目录 + 网盘」，不是直连；冲突自动选边；2023-10 后无更新。它的 App 库是从 Mackup 导的 |
| App 配置路径库 | **不导入 Mackup** | 曾计划用 lra/mackup 的 608 个 App 定义做路径库；App 偏好逐键同步下线后（§4.7），只需要手工把独立文件 / 目录加进同步清单 |
| 收件箱用文件监听？ | **不用**，按需扫描 | `~/Library/Preferences`、`Containers` 会被系统和 App 不停写，监听会刷屏，也违背掌控感 |
| 语言 | **Swift** | 只用 Mac。配置读写（`CFPreferences`）、默认打开方式（`NSWorkspace`）、App 版本签名、plist 全是系统原生接口；Go 只能到处调命令再解析输出。界面以后是 SwiftUI，同一个工程 |
| 第一版界面 | **SwiftUI 决策队列**，长文本合并交给 Zed | 拍板单位是条目和键，不需要 CodeMirror 那种行级合并组件 |
| 同步通道 | **中转站**：每台只操作自己，状态和决定经 `new` 服务器上的私有目录交换（ssh 传输）；**不经 ssh 远程拉起 agent** | ssh 拉起的进程不在桌面会话里，改默认打开方式、cfprefsd、launchctl 可能不生效；完全磁盘访问会被算到 sshd 头上，等于给所有 ssh 登录开权限；还要求两台同时在线，家里 MacBook 经常合盖。中转站方案三个问题都没有，顺带留下完整历史 |

讨论过程：Claude 与第一个 AI（主张 fork unisync）、第二个 AI（主张 Unison 底座 + 编排层）、Grok（主张自写单一对账器）多轮讨论后收敛到本方案。

## 3. 架构

```
┌──────── 家里 ────────┐        ┌──────── 中转站（new）────────┐        ┌──────── 公司 ────────┐
│ sssync.app            │  发布  │ 家里的最新状态               │  取回  │ sssync.app            │
│  · 扫描本机           │ ─────► │ 公司的最新状态               │ ◄───── │  · 扫描本机           │
│  · 对比、拍板         │        │ 基线（上次一致时的值）       │        │  · 对比、拍板         │
│  · 只在本机应用       │ ◄───── │ 待办决定（给家里 / 给公司）  │ ─────► │  · 只在本机应用       │
│  · 执行给自己的待办   │  取回  │ 应用回执、历史               │  发布  │  · 执行给自己的待办   │
└───────────────────────┘        └──────────────────────────────┘        └───────────────────────┘
```

**核心规则：每台机器只改自己。** 不远程执行任何东西。所有读写配置、改默认打开方式、重载启动项的操作，都在本机桌面会话里、以 sssync.app 自己的授权完成。

### 3.1 一次同步怎么走

1. **发布**：每台的 sssync 扫描本机，把状态（每个条目的规范化值和指纹，加上文本 / plist 的内容）上传到中转站。触发时机：打开 App、手动点扫描、常驻时定时（如 30 分钟）、开盖唤醒。
2. **对比**：我坐在哪台前面，就在哪台上看。对比的是「本机实时状态」vs「对面最近一次发布的状态」，界面明确标出对面状态的时间（如「家里 · 2 小时前」）。
3. **拍板**：每条差异选「用家里 / 用公司 / 合并 / 跳过 / 改策略」。
4. **执行**：
   - 本机要改的 → 立刻在本机应用；
   - 对面要改的 → 写成**待办决定**放到中转站。
5. **对面应用**：对面的 sssync 下次运行（开盖、定时、打开 App）时取回给自己的待办，在本机应用，写回执。
6. **基线更新**：一个条目两边都确认到同一个值，中转站的基线才更新为这个值。

### 3.2 待办决定

```json
{
  "id": "2026-11-06T10:21:03-007",
  "target": "home",
  "item": "file:~/.config/kaku/kaku.lua",
  "expect": "sha256:…",      // 拍板时看到的、目标机器上的当前值指纹
  "value": "blob:sha256:…",  // 要写成的值
  "decidedOn": "work"
}
```

- **前置条件**：目标机器应用前先核对本机当前值的指纹是否等于 `expect`。不等，说明拍板之后那边又改过，这条决定**作废**，回到待拍板队列，绝不覆盖。
- **应用方式**：默认自动应用并发系统通知（决定已经是我拍过的）；可按条目或全局改成「到那台时再确认」。preflight 不通过就挂起，等条件满足或我处理。
- **回执**：成功 / 作废 / 失败原因，写回中转站，发起那台的界面上能看到。

### 3.3 中转站

- 位置：`new:~/sssync-relay/`，经 ssh（`~/.ssh/config` 的 `new`）读写；两台本来就能直连 `new`。
- 结构：

  ```
  sssync-relay/
    machines/home/state.json      家里最新状态（条目 → 指纹 / 值引用）
    machines/work/state.json
    blobs/<sha256>                 内容按哈希存，只传新增的（增量）
    base.json                      基线：每个条目上次一致时的值
    decisions/<target>/<id>.json   待办
    receipts/<id>.json             回执
    history/                       旧状态和决定，按天归档
  ```

- 每台只写自己的 `machines/<me>/` 和发给对方的 `decisions/<对方>/`；写入一律「临时文件 + 改名」，两台不会写同一个文件。`base.json` 由应用回执驱动更新，加简单的文件锁。
- 中转站里有 `secrets.zsh` 这类敏感内容；`new` 是自己的服务器、走 ssh，安全级别与现在相同。目录权限 700。
- 中转站连不上时：本机决定照常应用，发给对面的待办暂存本地，恢复后补传。
- 连接：一次刷新的多次 ssh / rsync 复用一条连接（`ControlMaster`，socket 在本用户临时目录）；连上后断网 15 秒内发现（`ServerAlive`），每条命令另有总时限。失败时关掉复用连接重连一次（中转站上的操作都可以重做），不会把刷新挂死。
- `shared.json` 两台都会改：改之前先取中转站上最新的那份，只在上面改动这次碰到的字段，不用本机缓存整份覆盖。

### 3.4 组件

- **一个 Swift Package**：
  - `SyncKit`：库。Provider、对账器、执行器、中转站客户端、本地存储。
  - `sssync.app`：SwiftUI 界面 + 常驻（登录项，菜单栏图标）；负责定时发布、取回和执行待办。
  - `sssync`：命令行，同一套 SyncKit，用于调试和脚本（`sssync scan` / `publish` / `pull` / `status`）。
- **本地数据目录** `~/Library/Application Support/sssync/`：
  - `sssync.sqlite`：条目、策略、本机执行日志
  - `backups/<会话 id>/`：被覆盖内容的备份
  - `machine.json`：本机身份（`hw.model` → home / work）和模板变量
- **权限**：完全磁盘访问只授权给 sssync.app 一个。
- **以后的在线模式**：两台都醒着时，可以让两边常驻的 sssync 经 ssh 管道直接互通，做到即时刷新和即时应用。ssh 只当管道，不负责拉起进程；数据格式与中转站相同。第一版不做。

## 4. 条目与 Provider

### 4.1 条目（Item）

一切被管理的东西都是条目，有唯一 id，例如：

```
file:~/.claude/CLAUDE.md
dir:~/.claude/skills/pai                 （目录按顶层子目录聚合为一条）
agent:com.jiezaichan.rtunnel-new
app:dev.zed.Zed
handler:net.daringfireball.markdown
```

### 4.2 Provider 接口

```swift
protocol Provider {
    func scan(_ scope: Scope) async throws -> [ItemState]      // 现状：规范化值 + 指纹
    func render(_ local: ItemState, _ remote: ItemState, base: ItemState?) -> DiffModel
    func preflight(_ item: ItemID, target: ItemState) -> [Blocker]  // 如 App 正在运行
    func apply(_ item: ItemID, target: ItemState) async throws     // 在本机写入
    func postApply(_ items: [ItemID]) async throws                  // 重启 App、重载 launchd…
}
```

`apply` 永远只在本机调用。对面的修改由对面的 sssync 取回待办后调用它自己的 Provider 完成。

### 4.3 第一版的 Provider

| Provider | 规范化值 | 应用方式 | 要点 |
|---|---|---|---|
| **文件** | SHA-256；文本文件额外保存内容作为基线（≤ 2 MB） | 先备份 → 写临时文件 → 校验 → 原子改名，保留权限和 mtime；目录用 rsync `--files-from` 只传拍板过的文件 | 目录按顶层子目录聚合；软链按链接本身同步；遇到 `.git` 目录自动排除 |
| **启动项** | 规范化后的 plist 字典 | 写文件后 `launchctl bootout` + `bootstrap`，再检查是否起来 | 三种策略：同步 / 模板 / 本机专属；引用的程序路径在对面不存在时标红 |
| **默认打开方式** | 每个文件类型（UTI / 扩展名）和 URL scheme → 默认 App 的 bundle id | `NSWorkspace.setDefaultApplication(at:toOpen:)` / `toOpenURLsWithScheme:` | 目标 App 本机没装时，先按等价映射找替身（`Zed i18n` ↔ `Zed`），找不到就挂起并提示「先装 xx」；改浏览器（http / https）系统会弹确认框 |

实测（2026-11-05）：`.json` 家里是 VS Code、公司是 Zed i18n；`.md` 家里 VS Code、公司 WorkBuddy；`.yaml` 家里 VS Code、公司 Xcode。

### 4.4 App（报告 + 只改本机）

| Provider | 已实现 | 以后 |
|---|---|---|
| **App** | 列出两边缺什么、版本差多少、来源（brew cask / App Store / 手动安装）；本机缺的或旧的：brew 一键安装 / 升级，App Store 打开商店页安装 / 更新；本机多出来的：brew 装的 `brew uninstall --cask`，其余移到废纸篓（先退出；App Store 装的归 root，交给访达删，会要密码） | 直装 .app 经中转站传包 |

App 和工具链不进拍板队列：安装 / 升级只在本机点，对面缺的只给命令复制。卸载可以在本机点，也可以「让对面卸载」——写成 `uninstall:<行 id>` 待办（expect = 拍板时看到的对面的值），对面刷新时先执行它、按自己当时的报告重算这一行，值一致且确实是多出来的那台才卸，回执写到 `notices/<发起机器>/` 给发起那台看。对面卸 App Store 的 App 只试移到废纸篓，要密码的会失败并提示到那台上手动点。卸载只给「这台有、对面没有」的，两边都有只是版本不同的给升级。所有卸载先弹确认，写清要执行什么。

### 4.5 模板

同名不同参的条目（如 `rtunnel-new`）设为「模板」策略：

- 模板文件本身参与同步，变量用 `{{port}}`、`{{key}}` 占位；
- 每台的变量值写在本机 `machine.json`，**本机专属，不同步**；
- 应用时按本机变量渲染出真正的 plist，再重载。
- 对账比的是模板本身，不比渲染结果。

### 4.6 Shell 环境与开发工具链

**Shell 配置（zsh）** 走文件 Provider，但要先定一个约定，否则「同一份配置、个别值不同」没法同步：

- **共用部分**：`~/.config/zsh/` 下的 `zshrc`、`env.zsh`、`alias.zsh`、`functions.zsh`、`completion.zsh`、`bin/` → 策略「同步」。
- **本机部分**：新增 `~/.config/zsh/local.zsh`，由共用的 `zshrc` 在最后 `source`（不存在就跳过）→ 策略「本机专属」。只属于一台的环境变量、PATH、代理、别名都放这里。
- **密钥**：`secrets.zsh` 策略「同步」，但在界面上**不显示值**，对比只显示「哪些变量名变了」。
- `~/.zshrc`、`~/.zprofile`、`~/.zshenv` 只保留一行 `source ~/.config/zsh/zshrc` 之类的壳，作为普通文件同步。
- 自写脚本统一放 `~/.config/zsh/bin/` 并加入 PATH，`~/.local/bin/` 只留第三方安装器生成的东西。
- 公司 `myzsh` 仓库：`.git` 排除在同步外（与 skills 同理），git 只作为历史记录，两边各自保留。
- **环境变量的对比**：除文件对比外，Shell Provider 额外提供一个「生效后的环境」视图——每台发布状态时顺带跑一次 `zsh -lic env` 一起上传，按变量名逐个对比（PATH 拆成逐项列表），这样能看出「文件一样但效果不一样」的情况（例如某个目录只在一台存在）。只读，不直接改变量，改要回到文件。

**开发工具链** 是一个新的 Provider 类型，规范化值是「装了哪些版本 + 默认版本 + 每个版本下的全局包」：

| 工具 | 采集 | 应用 |
|---|---|---|
| nvm / node | `~/.nvm/versions/node/*`、`nvm alias default`、每个版本的 `lib/node_modules`（包名 + 版本） | `nvm install <版本>`、`nvm alias default <版本>`、`npm i -g <包>@<版本>`（nvm 是 shell 函数，必须在 `zsh -lc` 里执行） |
| uv / Python | `uv python list --only-installed` | `uv python install <版本>` |
| 其他（bun、deno、go、pnpm……） | 版本号 | 只提醒，或用自定义命令接入 |

- 每个版本、每个全局包都是一个条目，可以单独设策略（例如 node 16 设为「本机专属」或直接卸掉）。
- **全局包按「包」对账，不按「版本目录」**：同一个包在两边装在不同 node 版本下也能对上，并提示「家里装在 20.19.5，公司装在默认版本」。
- 已实现：在本机安装 / 升级 / 卸载（`nvm install|uninstall`、`npm install|uninstall -g`、`uv python|tool install|uninstall`、`brew install|upgrade|uninstall`），命令在 `zsh -lic` 里跑，弹面板边跑边看输出，跑完自动刷新。默认 node 版本不给卸载；全局包装在几个 node 版本下就从几个下面卸。

### 4.7 App 的配置怎么同步

App 偏好不逐键同步（2026-11-06 下线）。需要两台一致的 App 配置按它实际存放的位置走文件 / 目录条目：

- 存成独立文件的（Zed 的 `~/.config/zed`、Kaku 的 `~/.config/kaku`）直接加进同步清单；
- 只存在偏好域里的（iTerm2、Manico）用 App 自带的同步机制，或手工维护；
- **等价 App**：`dev.zed.Zed ≡ dev.zed-i18n.Zed`，App 和默认打开方式比对时视为同一个。
- **ego lite 不做文件同步**：基于 Chromium，Cookie / 登录态用各机钥匙串里的密钥加密，硬拷会坏。用它自带的账号同步；sssync 最多同步书签和扩展清单。

## 5. 对账与执行

### 5.1 策略

| 策略 | 含义 |
|---|---|
| 同步 | 参与对账，有差异进决策队列 |
| 本机专属 | 登记在案，永不同步，两边不同是正常的（灰显） |
| 忽略 | 不扫描、不显示 |
| 只提醒 | 有变化时进收件箱，但不给覆盖建议 |
| 模板 | 见 §4.5 |
| 确认差异 | 记下确认那一刻两边值的签名，差异从待处理里消失；任一边再变、签名对不上就重新出现。适用于同步条目、环境、应用。目标是「待处理」清零 |

可设在任意层级（Provider → App / 目录 → 文件 / 键），下层覆盖上层。另可设**方向锁**：某条只允许「家 → 公司」或反向。

### 5.2 对账结果

基线 = 上次两边达成一致时的值（存在中转站 `base.json`）。「对面」= 对面最近一次发布的状态。对每个条目：

| 状态 | 条件 | 默认建议 |
|---|---|---|
| 一致 | 本机 = 对面 | 不显示 |
| 只本机改了 | 本机 ≠ 基线，对面 = 基线 | 本机 → 对面 |
| 只对面改了 | 反之 | 对面 → 本机 |
| 两边都改了 | 都 ≠ 基线且彼此不同 | **冲突，必须拍板** |
| 改成一样了 | 都 ≠ 基线但彼此相同 | 只更新基线 |
| 新增 / 删除 | 一边有一边无 | 按上面规则；删除方向标红，必须明确确认 |
| 首次 | 无基线 | 只要不同就算冲突 |
| 等对面应用 | 已有发给对面的待办，还没回执 | 不再重复提示，显示「等待家里 / 公司应用」 |
| 等对面刷新 | 这一项的规则（是否归清单管、目录忽略、模板变量）和对面发布状态时用的不同 | 对面的值不可信（可能只是没扫），不给拍板按钮、不写基线 |

对账前两边都按**当前清单**过滤：清单外的条目（含新加的忽略规则）不参与，免得对面旧状态里的条目被当成「本机删了」推过去删掉对面的真实值。每台的 `state.json` 带上扫描时的规则（`Scope`），用来判断上面的「等对面刷新」。

### 5.3 执行的不变量

每台只在本机执行，每条决定（不管是本机当场拍的，还是取回的待办）按固定顺序，任何一步失败就停在这一条：

1. **核对前置条件**：本机当前值的指纹 = 拍板时看到的值；不等则作废，回到待拍板；
2. **备份**本机现有值到 `backups/<会话>/`；
3. **写入**（临时文件 + 原子改名 / 系统调用）；
4. **校验**：重新读本机，指纹必须等于决定的值；
5. **写回执**到中转站，并写本机执行日志；两边确认一致后更新基线。

由此保证：

- 执行到一半被打断（合盖、断网），已完成的条目有回执，未完成的保持原状；下次运行自动继续剩下的。
- 撤销 = 按日志逆序用备份写回，并发布新状态，让对面看到。整次撤销只撤本机这一侧；对面那一侧的撤销作为待办发过去。
- 只有一份「真相」：基线只存在中转站。

### 5.4 三方合并（文本）

两边都改过的文本文件（如 CLAUDE.md）：

1. 用中转站里的基线内容 + 两边现状做三方合并；
2. 不冲突的块自动合入，冲突块写成标准冲突标记；
3. 生成合并稿，用 Zed 打开编辑，保存即为这一条的决定；
4. 合并稿在本机直接应用，同时作为待办发给对面；两边都应用后基线更新为合并结果。

没有基线时（首次）退化为两方对比，Zed 左右打开，我手动编辑出结果。

## 6. 监控、跨机提醒与噪音过滤

### 6.1 目标

公司在同步清单里的某个文件改了 → 家里的 sssync 弹通知「公司改了 CLAUDE.md」→ 我决定要不要抹平。
但日志、缓存、窗口位置这类**必然不同**的东西不进同步清单，永远不提醒。

### 6.2 监控怎么做

- 不做实时文件监听（很多目录会被系统和 App 不停写，监听会刷屏）。
- 常驻的 sssync 定时（默认 15 分钟）+ 开盖唤醒时扫描**监视集**，与上一次发布的状态比较；有变化就发布到中转站。
- 对面的 sssync 取回时，发现「对面的值变了、而本机没变」→ 进「待同步」，并发**系统通知**（同一目录的多处变化合并成一条，如「公司改了 ~/.config/zsh 的 2 个文件」）。
- 监视集 = 同步清单里的文件和目录 + 启动项 + 默认打开方式 + App / 工具链只读报告。

### 6.3 App 配置怎么纳入

App 的配置不逐键扫描（见 §4.7）。存成独立文件或目录的，把那个路径加进同步清单，之后完全按文件 / 目录条目处理。

### 6.4 噪音过滤

1. **版本库元数据**：任何受管目录里的 `.git` 一律不扫描、不对比，规则写在扫描逻辑里，不依赖清单配置。
2. **目录级 ignore**（`DirSpec.ignore`，通配，按名字或相对路径）：`.DS_Store`、`node_modules`、`__pycache__`、锁文件、日志缓存等，写在同步清单里，两台共用。
3. **文件级例外**：`db-query/scripts/.env` 这种本机配置放进所在目录的 ignore，或把整个目录标成本机专属。
4. **不扫描偏好设置目录**：`~/Library/Preferences`、`~/Library/Containers` 会被系统和 App 不停写，不纳入监视集，避免刷屏。

### 6.5 收件箱（发现新东西）

新出现、尚未设策略的东西进收件箱：新装的 App、新的 LaunchAgent、受管目录里的新文件、对面新发布的条目。每条四个按钮：同步 / 本机专属 / 忽略 / 稍后。归类后写入策略，不再问。

## 8. 第一版（MVP）范围

**做**

- 中转站：发布状态（内容按哈希增量上传）、取回对面状态、待办决定、回执、基线
- 常驻：登录项 + 菜单栏，定时 / 唤醒时发布并执行给自己的待办；对面配置变了发系统通知（§6.2）
- 对账器、策略表、执行日志、备份与撤销
- 文件 Provider（含目录聚合、三方合并稿）
- Shell 配置（按 §4.6 的共用 / 本机 / 密钥约定），环境变量对比视图
- 启动项 Provider（同步 / 模板 / 本机专属）
- 默认打开方式 Provider（含等价 App 映射）
- App、开发工具链（nvm / uv 等）：只读报告
- SwiftUI 决策队列 + 同步状态栏 + 收件箱

**不做**

- 自动选边、按修改时间判断
- 远程执行（经 ssh 拉起进程）；在线模式（两边常驻进程直连）
- 通用同步协议、重命名检测
- chezmoi、Unison 作为引擎
- 钥匙串、登录态、激活码、TCC 授权（只提醒）
- 项目代码同步（只用 git）
- 魔改 App（以后用「补丁配方」：原版 + 改动文件 + 重签名步骤）
